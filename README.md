# jdd-fuzzer

jdd-fuzzer is the fuzzing part of JDD(<ins>J</ins>ava <ins>D</ins>eserialization Vulnerability <ins>D</ins>etector), which is designed and implemented by Xinyou Huang and Bofei Chen from Fudan University.
For more details, please read our [paper](https://ieeexplore.ieee.org/abstract/document/10646692)!

Static Gadget Chain Detection module is [here](https://github.com/fdu-sec/JDD).

## Installation


### Environment Preparation

The recommended OS is <ins>Unbuntu 18.04</ins> as it's the platform I am using to develop and running jdd-fuzzer. 

You also need <ins>[Maven](https://maven.apache.org/)(version 3.9.2 is prefered)</ins> and writing a shell script named `.bash_profile_mvn` under the home directory to specify the runtime environment variable required to run `mvn`.  

Besides, a <ins>custom `junit-quick-check`</ins> is also neccessay, which you can find [here](https://github.com/hn1e13/quick-check-for-jdd). Just simply run `install.sh`, and make sure it is installed in the local maven repository.

After all prerequisites are done, run `build_jdd.sh` to complile and install jdd-fuzzer.

### The Configuration File

A configuration file named `config.properties` should exist under the `config/` directory where the jdd-fuzzer is running. Checking out the following section for more details: 

```properties
# Time limitation for sigle gadget
fuzzTime = 60
# The absolute path to run jdd-fuzzer
work_dir = /the/folder/where/you/run/jdd-fuzzer
# The folder contains all inputs of jdd-fuzzer, this folder is located under `work_dir`
projectsInputDir = inputs
# The folder contains all IOCDs of gadget, this folder is located under `work_dir/projectsInputDir`
gadgetInfos_dir = gadgets
# A file to config the classes wont load into soot, this folder is located under `work_dir/projectsInputDir`
ignoreListPath = config/ignoreClasses

# The folder of jdd-fuzzer results, this folder is located under `work_dir`
outputDir = outputs
# The binary serialization files of explitable gadget chains, this folder is located under `work_dir/outputDir`
exploitable_dir = exploitable

# We would use some functions of soot, this option specify if load all jdk jars into soot or not.
withAllJdk = false
# The folder that contains jar/war/class file to bed analysised. Notice: The path string should be end with '/'
inputClassPath = lib/
```

### Intermediate Results from jdd-detector
Before running the jdd-fuzzer, both the `IOCDs` and `instrumentation information`, generated by jdd-detector, are needed to put in a correct loacation.  

For IOCDs, put them under the `gadgets` folder configured in `config.properties`.  

For instrumentation information, put them under the `files` folder where you start jdd-fuzzer.

### Start Fuzzing
#### (Recommended) Using `src-deploy/run_app.sh`: the way the evaluation was run
The evaluation runs one application at a time: a directory with the application's jars, and a directory with its IOCDs
(plus `IfStmtRecord*.json`). Set up the runtime JDK and build once, then:
```bash
src-deploy/setup_jdk.sh /path/to/jdk-8u361-linux-x64.tar.gz     # once: Oracle JDK 8u361, the JDK the IOCDs were produced with
src-deploy/build.sh                                              # once: build jdd-fuzzer
src-deploy/run_app.sh <out_dir> <jar_dir> <iocd_dir> [tries=3] [shards=nproc] [fuzz_time_sec=60]
src-deploy/replay/replay_check.sh <out_dir> <iocd_dir> <jar_dir> # replay what was found in a plain JVM, independently of the fuzzer
python3 src-deploy/analyze_run.py <out_dir> <iocd_dir>           # outcome per IOCD, distinct chains
```
Each IOCD is fuzzed on its own in fresh JVMs, for up to `tries` tries of `fuzz_time_sec` seconds each, and it stops at the
first success, <ins>in order to minimize the influence of randomness and program state on the effectiveness of fuzzing</ins>:
the fuzzer can fall into local optimality under certain circumstances, which is why an IOCD is fuzzed in several fresh JVMs
rather than one long run. The evaluation used 2 tries of 60 s per IOCD, 4 shards in
parallel, and the Oracle JDK 8u361 at run time (`src-deploy/env.sh` enforces it: the IOCDs match its sources line by
line, OpenJDK builds do not).

**Run in parallel.** `run_app.sh` splits the IOCDs over `shards` work directories and fuzzes one IOCD per shard at the same
time. Each shard has its own work directory, start file and payload directory, so they do not interfere. Use as many shards
as CPU cores (the default).

If static analysis detects a large number of gadget chains (IOCDs), you can parallelize their validation to improve efficiency and complete the process within the limited time available.



#### (Not recommended) Using `build_run_jdd_fuzzer.sh`
Additionally, you can also put all IOCDs under the folder specified in `config.properties` and run `./build_run_jdd_fuzzer.sh` to fuzz. After the instrumentation the fuzzer waits for the start file `/tmp/jdd_start_test`: run `./touch_jdd_start_file.sh` (or `touch /tmp/jdd_start_test`) to start it. `src-deploy/run_app.sh` does this for you.

## Reproducing the evaluation
`./reproduction/reproduce.sh` deploys the environment under test and runs the fuzzer on all 20 evaluated applications
(at most 6 hours each), replays what it finds in an independent JVM and counts the distinct confirmed gadget chains
per application. See [reproduction/README.md](reproduction/README.md); our results are in
[reproduction/SUMMARY.md](reproduction/SUMMARY.md), and the verified IOCDs in
[GroundTruth/](GroundTruth/).

**The IOCDs it fuzzes** are the ones our static module (jdd-detector) detected, per application, in
[fdu-sec/JDD: `IOCDDatasets`](https://github.com/fdu-sec/JDD/tree/main/IOCDDatasets) (`detected/<application>/`: the IOCDs
`<hash>.json` and the instrumentation records `IfStmtRecord*.json`). `reproduction/reproduce.sh` fetches them itself
(`src-deploy/fetch_data.sh`, pinned to the commit the results were produced with).

## Running Example
Run JDD-Fuzzer on one application, end to end (deploy, fuzz, replay in an independent JVM, count the distinct gadget
chains) with `run_single_app.sh`. Its input is what the static analysis module (jdd-detector) produced for the
application, the IOCDs (`<hash>.json`) and `IfStmtRecord.json`, plus the application's jars:
```bash
./run_single_app.sh <iocd_dir> [--work_dir <work_dir>] [--inputClassPath <jar_dir>]
```
e.g., Wicket (one IOCD; its IOCDs are in the [dataset](https://github.com/fdu-sec/JDD/tree/main/IOCDDatasets)), with
`JDD_JDK_TARBALL` pointing to the Oracle JDK 8u361 archive (only needed until the JDK is installed):
```bash
JDD_JDK_TARBALL=/data/jdk-8u361-linux-x64.tar.gz \
./run_single_app.sh /data/JDD/IOCDDatasets/detected/Wicket \
    --work_dir /tmp/jdd-wicket \
    --inputClassPath /data/jars/Wicket
```
```
/data/JDD/IOCDDatasets/detected/Wicket/     <iocd_dir>
    1310497851.json                         the IOCD
    IfStmtRecord.json                       the instrumentation record
/data/jars/Wicket/                          <jar_dir>
    slf4j-api-1.7.21.jar
    wicket-util-6.23.0.jar
```
The arguments correspond to `config.properties` (see above); only the first is required:

| argument | `config.properties` | |
|---|---|---|
| `<iocd_dir>` | the IOCDs in `gadgetInfos_dir` | required: the IOCDs and `IfStmtRecord.json` of the application |
| `--work_dir <work_dir>` | `work_dir` | optional: where the script works and writes its results (default `reproduction/runs/<date-time>`); run again with the same `<work_dir>` to resume |
| `--inputClassPath <jar_dir>` | `inputClassPath` | optional: the directory with the application's jars, copied to `inputs/lib/` of every shard, which is what `inputClassPath = lib/` refers to; without it only the JDK classes are analysed |

**The script creates `config.properties` itself**, you do not write it. For every shard (one fuzzer JVM, `SHARDS`) it
writes `<work_dir>/<application>/shard-<i>/config/config.properties`, with `work_dir` set to that shard's directory and
the other keys at their defaults (`fuzzTime` is `FUZZ_TIME`, 60 seconds):
```properties
fuzzTime = 60
work_dir = /tmp/jdd-wicket/Wicket/shard-0
projectsInputDir = inputs
gadgetInfos_dir = gadgets
ignoreListPath = config/ignoreClasses
outputDir = outputs
exploitable_dir = exploitable
withAllJdk = false
inputClassPath = lib/
```
The result table is `<work_dir>/SUMMARY.md`; `<work_dir>/<application>/` holds the per-IOCD outcomes (`analyze.out`,
`per_iocd.csv`), the replay verdicts (`replay.csv`), the distinct chains (`chains.csv`; each replay-confirmed chain also
as its own file `distinct_chains/<key>.txt`) and the payloads (`shard-*/outputs/exploitable/`). The other settings (`APP_TIME_LIMIT`, `TRIES`, `FUZZ_TIME`, `SHARDS`, `SEED`) are
environment variables, see the header of `run_single_app.sh`.
